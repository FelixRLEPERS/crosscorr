# Git-чек-лист для семьи CrossCorr

Практическое руководство по работе с git для Алексея, Макара (13) и
Егора (11). Дополняет [CONTRIBUTING.md](../../CONTRIBUTING.md).

---

## 1. Принципы

| Принцип | Что это значит |
|---|---|
| Маленькими шагами | Один коммит — одно понятное изменение. Не смешивать данные и код. |
| Понятные сообщения | Сообщение объясняет «зачем», а не «что». Через месяц поймёшь сам. |
| Ветка на каждую задачу | В `main` попадает только проверенный код. Работаем в `feature/...`. |
| Тесты перед коммитом | Сначала `pytest`, потом `git commit`. Красные тесты не коммитим. |
| Ревью всегда | Даже папин код смотрит второй человек. Даже детский — Алексей. |
| Секреты не коммитим | `.env`, `opencode.json`, ключи, пароли — только локально. |

## 3. Формат сообщения коммита

Используем **Conventional Commits**: `<тип>(<область>): <суть>`.

Типы: `feat`, `fix`, `test`, `docs`, `chore`, `refactor`, `ci`, `style`.

Примеры «плохо → хорошо» под CrossCorr:

Плохо:
```
update
```
Хорошо:
```
feat(pairs): добавил опцию --n-jobs в CLI
```

Плохо:
```
fix bug
```
Хорошо:
```
fix(surrogate): NaN в фазовом суррогате обнулял p-value
```

Плохо:
```
папа починил
```
Хорошо:
```
fix(pairs): закрыл утечку shm через ExitStack

Причина: при сбое создания второго SharedMemory первый не удалялся.
```

Плохо:
```
добавил данные
```
Хорошо:
```
data(samples): 10 строк WSPR за 2024-03 (Егор)
```

Проверка: если прочитать только первую строку коммита — понятно, зачем он.

## 4. Ритуалы

### «Киноплёнка» (пятница)

В пятницу вечером запускаем тесты и всей семьёй смотрим результат:

```
python -m pytest tests/ -m "not slow" -q
```

Зелёное — повод для гордости. Красное — обсуждаем, чиним в выходные.
Ритуал: наклейка/стикер на монитор за каждую зелёную пятницу.

### «Первая ветка»

Каждый новый участник сам создаёт свою первую ветку и делает первый PR.
Ветку называем с именем: `feature/egor-wspr-rows`.

### «Археология» (раз в месяц)

Смотрим `git log --oneline -20` и отвечаем: что было самым важным за месяц?
Кто что сделал? Это учит читать историю, а не только писать.

### «Уборка перед сном»

Перед сном: `git status`. Если есть незакоммиченные изменения — решаем:
закоммитить или откатить. Не оставляем «грязь» на следующий день.

## 5. Практические правила

### Можно и нужно

- Создавать ветку под каждую задачу.
- Часто коммитить маленькими порциями.
- Запускать `pytest` перед коммитом.
- Спрашивать Алексея, если что-то непонятно.
- Читать `git diff` перед коммитом — глазами проверить, что меняешь.

### Нельзя без Алексея

- Править ядро: `surrogate.py`, `mantel.py`, `pairs.py`,
  `cross_correlation.py`.
- Менять `pyproject.toml`, `.github/workflows/**`, `Makefile`.
- Делать `git push --force`, `git reset --hard`, удалять ветки.
- Разрешать конфликты merge (это сложно, делаем вместе).
- Коммитить что-либо из `.env`, `opencode.json`, ключи.

### Учимся постепенно (по возрастам)

| Навык | Егор (11) | Макар (13) |
|---|---|---|
| `git status` / `git diff` | смотрит вместе | сам |
| `git commit` | через GitHub Desktop | через GitHub Desktop |
| Создать ветку | с помощью | сам |
| Запустить `pytest` | читает вывод вместе | сам |
| Открыть PR | с помощью | сам |
| Merge в `main` | нет | вместе с Алексеем |
| `git rebase` | нет | позже |
| Разрешение конфликтов | нет | вместе с Алексеем |

## 6. Структура веток

```
main                      # только проверенный код, всегда зелёный
├── feature/egor-wspr-rows    # Егор добавляет данные
├── feature/makar-plot-legend # Макар правит график
├── fix/papa-shm-leak         # Алексей чинит утечку памяти
├── test/makar-safe-exec      # Макар пишет тесты песочницы
└── docs/mama-readme          # Мама правит текст
```

Правила именования:

- Префикс по типу: `feature/`, `fix/`, `test/`, `docs/`, `chore/`.
- После префикса — имя автора и короткая суть.
- Одна ветка = одна задача. Сделал — открой PR, не копи в ней десять дел.
- Влили в `main` — ветку можно удалить.

````markdown
### Что сделал

### Зачем
<какую задачу или находку закрывает>

### Как проверить
```
python -m pytest tests/ -m "not slow" -q
```

### Тесты
- [ ] Добавил новый тест
- [ ] Или объяснил, почему тест не нужен

### Скриншот/вывод
<если применимо>

### Чек-лист
- [ ] CI зелёный
- [ ] Ветка называется по правилам
- [ ] Секретов в diff нет
````

## 8. Чек-лист перед коммитом

Задай себе 7 вопросов:

1. Что именно я изменил? (посмотрел `git diff`)
2. Зачем это нужно? (это и есть суть сообщения коммита)
3. Запустил `pytest tests/ -m "not slow" -q` — зелёно?
4. Не попали ли секреты (`.env`, ключи)?
5. Ветка правильная (`feature/...`, не `main`)?
6. Коммит маленький? (одна задача, а не десять)
7. Пойму ли я это сообщение через месяц?

Если хоть один ответ «нет» — остановись и разберись.

---

## 9. Чек-лист перед merge в main

- [ ] Все тесты зелёные: `python -m pytest tests/ -m "not slow" -q`
- [ ] CI на GitHub зелёный (все обязательные job'ы)
- [ ] Code review пройден (Алексей посмотрел)
- [ ] В diff нет секретов и случайных файлов
- [ ] Ветка синхронизирована с `main` (нет конфликтов)
- [ ] PR-описание заполнено, тест указан

Merge делает Алексей. После merge — запись в `docs/journal/`.

## 10. Что делать, когда что-то сломалось

| Ситуация | Что делать |
|---|---|
| `pytest` показывает красное | Не коммитить. Показать вывод Алексею. |
| Поменял не тот файл | `git restore <файл>` — откатить до сохранённого. |
| Сделал коммит не в ту ветку | Не паниковать, позвать Алексея (перенесём аккуратно). |
| Случайно закоммитил секрет | Сразу сказать Алексею: ключ нужно ротировать. |
| Конфликт при merge | Не разрешать самому — только с Алексеем. |
| Удалил что-то важное | `git log` найдёт старую версию. Ничего не потеряно. |
| Запушил не то в свою ветку | Ок, можно перезаписать свою ветку (но не `main`). |

## 11. Как это превращается в портфолио

- **История коммитов** — доказательство навыков. Понятные сообщения
  выглядят профессионально.
- **Pull Request** — показывает умение работать в команде и проходить
  ревью.
- **Ссылка на репозиторий** в портфолио: `github.com/FelixRLEPERS/crosscorr`.
- Разделы: «мои PR», «мои тесты», «мои данные».
- В интервью/школе можно рассказать: «я добавил тесты безопасности
  и поднял покрытие модуля».

Каждый вклад — строчка в будущее резюме. Даже 11-летнее «добавил
10 строк данных и прошёл ревью» это уже реальный опыт.

---

## 12. TL;DR — 7 правил на стену

1. Одна задача — одна ветка — один PR.
2. Сначала `pytest`, потом `commit`.
3. Сообщение коммита объясняет «зачем».
4. Маленькие коммиты лучше больших.
5. Секреты не коммитим никогда.
6. Сомневаешься — спроси Алексея.
7. В `main` попадает только зелёное и проверенное.
