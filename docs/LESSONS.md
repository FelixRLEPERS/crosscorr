## Уроки (операционные анти-паттерны)

Из сессии 2026-10-12 (релиз v1.1.0). Дополняют HANDOFF-уроки 1–8;
там же — специфика session 2/3 (worktree, cherry-pick, force-push).

### Windows / PowerShell

- **credential.helper.** GCM установлен
  (`git-credential-manager.exe` в `C:\Program Files\Git\mingw64\bin`,
  verified), но git о нём не знает, пока не сконфигурирован:
  `git config --global credential.helper manager`. Без этого push
  из PowerShell падает (`could not read Username for
  'https://github.com'`), даже если GitHub Desktop пушит из UI.
- **UTF-8 без BOM.** `Set-Content -Encoding utf8` в PS 5.1
  добавляет BOM (U+FEFF) в начало файла. Для записи UTF-8-без-BOM:
  `[System.IO.File]::WriteAllText($path, $c, (New-Object
  System.Text.UTF8Encoding $false))`.
- **Чтение UTF-8.** `Get-Content -Raw` в PS 5.1 читает файл как
  cp1251 на русской локали → не-ASCII превращается в моджеику при
  обратной записи (UTF-8 → cp1251-байты → UTF-8). Для корректного
  чтения: `[System.IO.File]::ReadAllText($path,
  [System.Text.Encoding]::UTF8)`. Симметрично с записью.
- **.NET cwd ≠ PS `$PWD`.** `[System.IO.File]::*` использует .NET
  current directory (обычно `C:\Users\<user>`), а не `Get-Location`.
  Относительный путь пишется не туда. Правило: перед .NET-API
  строить абсолютный путь через `Join-Path (Get-Location).Path $rel`.

- **`[Environment]::NewLine` = CRLF, не LF.** При работе с LF-файлами (write-tool, here-string, markdown этого репо) использовать LF-escape (backtick + n), а не `[Environment]::NewLine`. Иначе получается mixed-ending файл (LF + один CRLF), который ломает последующие regex/replace и загрязняет diff.

- **LF→CRLF warnings при `git add`** — ожидаемо на Windows (`core.autocrlf=true`); файлы пишутся в LF, git конвертирует в CRLF при checkout. Не ошибка. Cross-platform fix (`.gitattributes` `* text=auto eol=lf`) — в backlog.

- **PowerShell backtick.** В PS 5.1 обратная кавычка (`) является символом экранирования. При передаче inline-скриптов через `python -c "..."`, содержащих обратные кавычки (например, Markdown-код), PS съедает их, превращая в обратные слэши. Правило: сложные inline-скрипты со спецсимволами запускать только через сохранённый `.py` файл.

- **Нет `grep`; ревизии с `^{}` — в кавычках (session 2026-10-31).**
  `grep` в PowerShell 5.1 → `CommandNotFoundException`; замена —
  `Select-String -Pattern ... -Path ...` (grep-пункты DoD читать как
  Select-String). И `git rev-parse v1.6.1^{commit}` / `^{}` PowerShell
  ломает (fatal: ambiguous argument / парсер-ошибка) — аргумент всегда
  в одинарных кавычках: `git rev-parse 'v1.6.1^{commit}'`.

### Git

- **GitHub Desktop не пушит локальные теги автоматически** (опыт
  проекта, HANDOFF-урок 6). Push тега — только из CLI:
  `git push origin <tag>`. Дополняет урок 6: remote-тег может
  отличаться от локального (`v1.0.2-paper`: локально `00e692a`,
  remote `f97844e`); переписывать задним числом нельзя.
- **First commit of a new file.** write-инструмент не ставит final
  newline; pre-commit `end-of-file-fixer` допишет его и уронит
  коммит. Ожидаемо: re-add + повторный commit. Тот же класс, что
  W292 в `probe_ksg_ties.py` (CI #139).

- **`ruff-format` форматирует Python-код внутри Markdown.** Хук обрабатывает
  ```` ```python ````-блоки в `.md` (напр., `zenodo_data/README.md`). Если при
  коммите ruff переставил выравнивание в примере кода — это нормально, не
  откатывать: re-add + повторный commit (тот же класс, что W292/first-newline).
- **Не обходить `.gitignore` через `-f` молча.** Если файл из игнорируемой
  директории нужен в репо — добавляй явное исключение `!path/to/file` в
  `.gitignore`, а не полагайся на `git add -f`. Молчаливый `-f` маскирует
  намерение и «обходит политику» (опыт: `zenodo_data/README.md` временно
  добавлен через `-f`; исключение `!zenodo_data/README.md` — штатный путь).

- **Чеклисты и хэши — только над tracked-файлами (session 2026-10-31).**
  `checksums_*.txt`, манифесты и сверочные списки должны ссылаться
  исключительно на файлы из git: untracked-файл (опыт —
  `results/perm_test_18mo_3band_fdr.json`) не попадёт в клон с GitHub,
  и никто не сможет сверить хэши. Перед публикацией — `git ls-files`
  по каждому пути из списка.

### Python replace-скрипты (tmp_fix_*.py)

Урок сессии 2026-10-15 (batch 9-11). Применяется к скриптам в
стиле `tmp_fix_*.py`, которые делают серию `str.replace` /
`lines[i:i+n] = [...]` и один `write_bytes` в конце.

- **Двухфазный паттерн обязателен.** Phase 1 — verify: пройти по
  всем паттернам, собрать счётчики `text.count(old)`, **вывести
  все** несовпадения (не падать на первом). Phase 2 — apply:
  только если Phase 1 дала `all OK`, выполнять замены и
  `write_bytes`. Это спасает от частично применённого состояния.
  Пример корректной реализации — `tmp_fix_c1b.py` (session 11).

- **Диагностика перед повторным запуском.** Если `tmp_fix_*.py`
  **упал**, не факт, что файл не тронут: скрипт мог упасть
  **после** `write_bytes` предыдущего запуска, или быть запущен
  дважды подряд (как случилось с `tmp_fix_audit2.py`, session
  11 → дубль блока Session 10/11). Правило: перед любым
  повторным запуском — `git diff <target>` + dump окна вокруг
  ожидаемого anchor. Не запускать replace-скрипт «вслепую»
  второй раз.

- **Anchor с indent = риск.** Для многострочных паттернов с
  continuation-indent (`\t      `, `\t\t`) нельзя угадывать
  пробелы/табы. Надёжнее: либо **line-based** (`split(NL)` +
  поиск по `anchor_substr in line` + `lines[i:i+n] = [...]`),
  либо предварительный dump байтов: `python -c` с
  `repr(text[i:i+250])`. `tmp_fix_c4.py` (session 11) падал
  трижды именно на indent — пока не перешли на line-based.

- **Один скрипт = один логический пакет.** Не смешивать в одном
  файле замены из разных категорий (units, refs, таблицы). При
  провале одного паттерна откат бьёт по всем категориям. Если
  пакетов несколько — отдельные `tmp_fix_<topic>.py`,
  последовательные коммиты.

- **Никаких heredoc-инлайнов для LaTeX-правок (session 12).**
  `python - <<'PYEOF'` внутри Git Bash на Windows схлопнул
  `\\ref` → `\ref`, Python интерпретировал `\r` как CR — два
  `\ref` в main.tex молча превратились в битые макросы (поймано
  только при ревью diff следующего коммита). Правило: правки,
  затрагивающие обратные слэши, — только через записанный
  `tmp_fix_*.py` с Phase-1 verify. После любого автобайтового
  редактирования — dump `repr()` вокруг затронутых строк.

- **Генерация отступов LaTeX из Python (session 2026-10-30).**
  При генерации LaTeX из Python использовать `\t` только в начале
  строк или заменять на 4 пробела; literal `\t` (два символа
  `\` + `t`) перед `\item` в LaTeX вызывает ошибку LR-mode
  (accent tie на кириллице). Python-escape `"\t"` = реальный таб
  (0x09) — безопасен; ломает именно литеральный `\` + `t` в
  результате битой escape-обработки. Симптом — каскад ошибок
  (`Not allowed in LR mode`, ложное «not UTF-8») с первой строки
  `\t\item`. Проверка: grep `(?<!\\)\t(?![a-zA-Z])` по `.tex`,
  лечение — 4 пробела (пример: 9 строк Limitations в
  `main_ru.tex`, фикс в коммите `5a22dbb`).

- **read_text/write_text vs CRLF (session 12).** `read_text()`
  делает universal-newline-нормализацию CR→LF; смешение
  `read_text`/`write_text` на CRLF-файле переписывает все 1256
  строк (diff от «однострочной» правки). Итог: `git add` хранит
  CRLF в blob при `* text=auto`. Правило: только
  `read_bytes`/`write_bytes` + явная проверка BOM и переводов
  строк. Если CRLF всё же попал в blob: `git reset --soft HEAD~1`,
  нормализовать файл в LF, `git add`, закоммитить заново
  (renormalize при этом бывает пустым — не доверять ему вслепую).

- **Кириллица в математике (session 2026-10-30).** Никогда не
  используй `\mathrm{русский_текст}` внутри математического режима —
  LaTeX молча выдаст `Command \cyrXX invalid in math mode`, и
  числитель дроби исчезнет в PDF. Всегда используй
  `\mbox{русский_текст}` (стиль проекта, как `\mbox{Гц}` в SI).
  Проверка: `pdftotext` + grep на наличие кириллицы в формулах.

- **Длинные команды и LaTeX-лигатуры (session 2026-10-30).**
  `\verb|...|` не переносится → Overfull hbox и обрезка текста за
  краем. `\path{...}` схлопывает пробелы (`--source api` →
  `--sourceapi`). `\texttt{--}` лигует в en-dash (`–`). Решение для
  CLI-команд: `\texttt{...}` + `\_` + `-\kern0pt-` (разрывает
  лигатуру) + scoped `{\sloppy \par}` вокруг абзаца. Проверка:
  `pdftotext` + grep на полную строку с `--`.

- **Неиспользуемые метки (session 2026-10-30).** `\label{tab:spatial}`
  без `\ref{tab:spatial}` в тексте = висячая таблица. Рецензенты
  обращают на это внимание. Проверка: скрипт или grep, что каждый
  `\label{}` имеет хотя бы один `\ref{}`. Исключение — служебные
  метки (`eq:...` могут оставаться невостребованными).

- **Жёсткая дата в submission-.tex, не `\today` (session 2026-10-31).**
  `\today` делает артефакт «скользящим»: пересборка молча меняет дату
  в PDF (опыт: Cover Letter собран 30.10 = «October 30»; пересборка
  31.10 дала бы другую дату). Для писем/манускриптов к сабмиту дату
  фиксировать явно (`October 31, 2026`).

### Согласованность текста, выборок и данных (Q1-ревью, session 2026-10-30)

- **Семантическая синхронизация текста (session 2026-10-30).** При
  изменении методологии (например, AR(1) → tau_int, добавление
  TX-нормировки) недостаточно обновить только цифры в JSON.
  Обязательно делать `grep` по старым формулам (`ESS = N...`), старым
  DOI и названиям методов в тексте. Иначе рецензенты найдут
  противоречие между текстом и таблицами.

- **Разделение семейств оценок (session 2026-10-30).** Если в статье
  используются разные выборки (например, NB-модель на raw counts N=198
  и Perm-test на norm-tx N=169), это должно быть явно указано в
  Abstract, Key Points и Caption к каждой таблице. Никогда не смешивайте
  их в одном предложении без пометки.

- **JSON/CSV newline на Windows (session 2026-10-30).** Скрипты,
  сохраняющие результаты в `results/*.json`, должны использовать
  `write_bytes` с явным `\n` (LF), а не `json.dump()`, который на
  Windows может добавить CRLF. Это ломает pre-commit хуки и diff.
  (Урок подтвержден на `scripts/ess_tau_int.py`).

- **FDR artifact** — `perm_test_18mo_3band_fdr.json` (5000 iter, no add-one)
  is legacy; superseded by `round3_merge_sensitivity.json` +
  `perm_test_dst_50k.json`. Do not use in analysis.
- **Parquet drift** — the current `unified.parquet` (rebuilt 2026-10-30,
  sha 8ee0ac22…) does not bitwise reproduce analysis artifacts committed
  before that date (round3, perm_test_18mo_3band_fdr). Drift ~1e-6
  relative; below reporting precision (0.1 pp), above bit-identity.
  Rebuild any artifact by rounding to reported precision, not by
  comparing raw floats.

- **Point estimates vs CI in prose (session 2026-11-01).** Не пишите
  "изменение менее чем на X", если верхняя граница 95% CI выходит за X.
  В таких случаях явно указывайте, что это "point estimate", и добавляйте
  скобку с реальной границей CI. Иначе строгий рецензент (или аудит)
  поймает противоречие между текстом и таблицей.
  (Пример: Abstract "SNR changes by less than 0.5 dB" при CI 40 м до
  -0.56 дБ — исправлено в v1.6.2.)

### Долгие фоновые загрузки (метод part-файлов / resume)

Урок сессии 2026-10-27 (`download_stations_geo.py`: 3652 API-запроса,
~35–60 мин). Референс-реализация — docstring и `apply()` того же скрипта.

- **«Одна запись в конце» спасает артефакт, но убивает прогон.**
  Правило двухфазности (write один раз, в конце) корректно для
  итогового CSV, но промежуточные результаты многочасового задания
  обязаны чекпоинтиться. Факт: фоновый шелл opencode убил python
  без traceback на 73-й минуте (chunk 365/913), `.out`-лог шелла
  удалён вычисткой — все данные прогона потеряны, потому что жили
  только в памяти процесса.

- **Метод: одна задача = один part-файл.** Каждый завершённый
  запрос сразу пишет свой маленький CSV в
  `data/processed/<name>_parts/` через `tmp` + атомарный
  `Path.replace()`. Повторный запуск того же `--apply` читает
  список задач, отмечает существующие части как done и догружает
  только недостающее. Гигиена: удалять `_parts/` только после
  успешной финальной записи **и** пустого списка ошибок; при
  ошибках — оставить (это и есть resume), флаг `--clean` для
  сброса.

- **Параллелизм за счёт независимых файлов.**
  `ThreadPoolExecutor(jobs=N)` безопасен, когда у каждой задачи
  свой выходной файл и нет общего состояния; прогресс печатать из
  главного потока по `as_completed` + `flush=True`. `jobs=4`
  дало ~4× ускорение без rate-limit.

- **Лестница отказов вместо исключения в лоб.** Долгий прогон
  нельзя ронять из-за одного таймаута: (1) retry с backoff внутри
  запроса, (2) сплит по подмножествам (бэндам), (3) халвинг
  временного окна до 1 часа, (4) поштучный сбор `failed` +
  отдельные retry-пасы в конце. Одно необработанное `raise` в
  общем цикле = потеря прогона. Скрипт, который падает целиком при
  первом сбое сети, для публичных API непригоден.

- **Фоновый шелл opencode не гарантирует жизнь процесса.** Kill
  приходит без traceback, лог-файл шелла может быть удалён
  вычисткой. Для длинных задач: чекпоинты обязательны; свой лог
  в отдельный файл (`Tee-Object` переживает шелл); запуск через
  `python -u` — иначе stdout в pipe буферизуется и лог пуст до
  самого конца.

- **Пробы должны использовать ТОТ ЖЕ query shape, что и боевой
  прогон.** На db1.wspr.live Phase-1 «похожий» probe (unbounded
  DISTINCT) врал: таймаут 45–300 с, а реальный рабочий shape
  (1-дневное окно + band-фильтр, TX — по одному бэнду) отвечал
  за 0.2–0.4 с. Проbe нерабочего запроса = бесполезная Phase 1.
  Эндпоинт load-dependent: идентичные запросы проходят и падают в
  разное время — решать по устойчивости серии (ретраи), а не по
  одному замеру. Детали envelope — в docstring
  `data/scripts/download_stations_geo.py`.

- **Стабильный размер файла ≠ готовность (smoke-test stub).**
  Пока идёт многочасовая загрузка, промежуточный/старый файл
  (например, от смоук-теста) висит нетронутым и стабилен по
  размеру и mtime — проверка «файл существует и больше N байт»
  даст **false READY** на данных, которые ещё не докачаны.
  Триггер завершения — **exit code процесса-загрузчика** (0 =
  успех), а не размер/mtime/строки. mtime и row-count — вторичные
  санити-проверки (младше `--since` старта, ≥ `--min-rows`),
  самодостаточного readiness не дают. Смоук-ловушку поймали
  заранее: стаб 181 КБ висел бы с < 50 000 строк и ушёл в
  analysis как полный справочник.

### Гейты покрытия: проценты не спасают от неверного формата (false-pass)

Урок сессии 2026-10-29 (`spatial_analysis.py --source local`).

- **Гейт по Z≥90% недостаточен: формат входных данных надо
  валидировать ДО join** — `required_columns ⊆ columns` +
  `nunique(tx_call) > 0`. Факт: `local join: 99845/100000 (99.8%)`
  прошёл гейт, но таблица оказалась мёртвой — `N_storm=0` во всех
  трёх группах при exit 0. Причина: `wspr_hourly_*.csv` — часовые
  агрегаты (`spots_count`, `mean_snr`, ...), без `tx_call`/`rx_call`,
  т.е. сырых спотов с позывными локально нет; Z считался по часовым
  бакетам, а join-ключи валидны по количеству строк, но пусты по
  содержанию. Мёртвая таблица (N_storm=0, Drop% n/a) визуально не
  отличима от валидной — её ловит только явная проверка схемы
  входа и непустоты ключей **до** join, а не постфактум по
  покрытию. Правило: сначала `required_columns ⊆ columns` и
  `nunique(tx_call) > 0`, потом join, потом уже Z ≥ 90%.

### WSPR API: порог ~19 с на длинных запросах (trivial-probe false-pass)

Урок сессии 2026-10-30 (`spatial_analysis.py --apply`, flare control).

- **Симптом:** `db1.wspr.live` стабильно рвёт соединение
  (`ConnectionResetError 10054`) ровно на **19.1 с** — но только на
  «тяжёлых» запросах. `SELECT 1`, `LIMIT ≤ 500` и серверные
  `GROUP BY`-агрегаты (14-дневные чанки Phase 2, включая latbin)
  отвечают за 0.2–1.3 с. Порог не в размере ответа: без-latbin
  `LIMIT 1000` (57 КБ) проходит, с-latbin `LIMIT 1000` — reset.
- **Причина:** посредник на plain HTTP длинных соединений
  (среда Windows/регион с VPN-ограничением, см. AGENTS.md) убивает
  запрос, который думает дольше ~19 с; ClickHouse на row-level
  выборке с `ORDER BY id` + внешним latbin-выражением упирается
  в этот бюджет. Детерминировано: 3/3 попыток одинаково.
- **Затронуто:** только Phase-1 кроссчек `--sample-n`
  (`ORDER BY id LIMIT N` c radians/latbin) при `N ≥ 1000`.
  Phase 2 (`fetch_counts_api`) не затронут — его запросы
  агрегируются на сервере и быстрые.
- **Митигация:** `--sample-n 500` (кроссчек остаётся, на результаты
  Phase 2 не влияет) либо `--skip-crosscheck`. Дефолт `5000` в этом
  окружении нерабочий.
- **False-pass `wait_for_api.py`:** проба `SELECT 1` может вернуть
  «API is back!», тогда как целевой тяжёлый запрос всё ещё падает —
  тривиальная проба проверяет доступность хоста, а не бюджет
  длительности запроса. Ловить реальные падения можно только
  полноразмерным прогоном verify (он fail-loudly и не перезаписывает
  артефакты).
