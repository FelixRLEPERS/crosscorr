# ✨ Архитектурное обновление: Внедрение Source Registry Pattern (CrossCorr)

## 💡 Обзор и Проблема
До внедрения данного рефакторинга, логика обработки внешних источников данных была фрагментирована и жестко связана в коде. Каждое новое добавление источника (например, новый тип сенсоров или новые API-данные) требовало ручного изменения основного парсера (`api_client`), что создавало:
1.  **Риск расхождения:** Высокая вероятность пропуска обновления логики при добавлении нового источника.
2.  **Низкую масштабируемость:** Код становился громоздким и трудно поддерживаемым (God Object).

## 🚀 Решение: Source Registry Pattern
Мы внедрили паттерн **Source Registry**. Это централизованный, декларативный слой абстракции, который служит единым источником правды (`Single Source of Truth`) для всех известных источников данных в проекте.

### 📁 Что было изменено (Technical Deep Dive)

Внедрение включало изменения трех ключевых модулей:

1.  **`data/scripts/registry.py` (SourceRegistry):**
    *   Создан класс `SourceRegistry`, который содержит метаданные для каждого источника (`WSPR`, `INTERMAGNET`, `NGL`).
    *   Метаданные включают критически важную информацию: ожидаемые поля (`expected_fields`), скрипт загрузки и, что самое главное, **URL-контракт API** (`base_url` и `api_endpoint`).
2.  **`data/scripts/__init__.py`:**
    *   Внедрена автоматическая инициализация реестра при импорте всего пакета `data.scripts`. Это гарантирует, что реестр всегда заполнен, прежде чем начнётся выполнение скрипта.
3.  **`data/scripts/api_client.py`:**
    *   Основной класс был переработан для использования `SourceRegistry`. Вместо хардкода, он теперь **валидирует** каждый запрос через реестр, получая всю необходимую информацию о URL и параметрах напрямую из метаданных.

## ✨ Ключевые улучшения (Key Achievements)

| Характеристика | До рефакторинга | После Source Registry |
| :--- | :--- | :--- |
| **Масштабируемость** | Низкая. Требуется изменение ядра при добавлении источника. | Высокая. Добавление нового источника требует только добавления записи в `data/scripts/registry.py`. |
| **Контракт API** | Неявный. Зависит от структуры кода. | Явный и централизованный. Все контракты хранятся в реестре. |
| **Надежность** | Низкая. Высокий риск сбоев при изменении внешнего источника. | Высокая. Внедрена проверка `SourceRegistry.is_registered()` для предотвращения ошибок на этапе выполнения скрипта. |

## 🧪 Проверка и Тестирование
Мы разработали **`test_source_registry.py`**, который:
*   Проверяет, что все основные источники автоматически регистрируются (Unit Test).
*   Мокирует внешний запрос API для проверки полного цикла: `Registry -> Client -> Request`. Это подтверждает, что новая архитектура работает и сохраняет функциональность старых источников.

**Готовность:** Проект готов к приему новых источников данных с минимальными усилиями по поддержке кода!
